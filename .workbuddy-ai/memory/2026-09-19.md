## Prefill batched 2-bit (lanjutan) — 7,7 -> 81 -> 90,6 tok/s

Implementasi: `launch_qmm_sm75_b2_prefill_fp16` + `qmm_sm75_b2_kernel`
(namespace `bonsai::sm75::wmma_b2`), dipanggil dari `forward_prefill_device`
saat `bits == 2` (field baru `ffi_qmm2_ready`/`ffi_qmm2_fn`, alias
`CudaQmmPrefillB2FnFP16` di ops.mojo).

Hal yang wajib diingat:
- Kernel qmm 2-bit BUTUH parameter `n_total` terpisah (stride baris output),
  sebab ekor dense 96 baris (in_proj_b/a) menempati kolom [n_packed, n_total).
- FWHT prefill butuh buffer scratch M*K: `x_norm_m_dev` dipakai bersama q/k/v,
  jadi transformasi in-place SALAH. Scratch dialokasi sekali di main.mojo
  (`pf_fwht`, chunk_len × cfg.intermediate_size) dan diteruskan lewat
  layer.mojo -> forward_prefill_device. Aman dipakai bergantian karena tiap
  modul meng-enqueue FWHT -> GEMM berurutan pada stream yang sama.
- Jangan alokasi scratch per modul: 64 layer × K terbesar 17408 × 256 baris
  ≈ 1,1 GB VRAM.

Pengukuran (prompt 129 token, T4): fallback 129 ms/token (7,7 tok/s) ->
BM=64: 12,32 ms/token (81,2) -> versi PRMT: 12,28 (81,4, TIDAK berpengaruh)
-> BM=128 + lompat ubin 16 baris bantalan: 11,03 ms/token (90,6 tok/s).

Pelajaran:
- **ptxas sudah membuat PRMT sendiri** dari rangkaian banding/select. Ukuran
  `.so` identik ke byte adalah petunjuk kuat bahwa perubahan sumber tidak
  berdampak pada SASS. Jangan mengoptimasi operasi skalar dekuantisasi.
- Yang menentukan adalah **jumlah pass dekuantisasi bobot = ceil(M/BM)**.
  BM=128 untuk M=129 menghemat 33% pass → +11,4%.
- Perbandingan prefill 1-bit (124 tok/s) TIDAK setara: diukur pada prompt
  56 token, sedangkan 2-bit pada 129 token. Jangan dikutip sebagai gap
  tanpa menyebut perbedaan panjang prompt.

## Audit referensi llama.cpp-prism — ada yang lebih baik (ya)

Permintaan user: "cek llama.cpp. apakah disana ada yang lebih baik ngg."
Diverifikasi dengan membaca sumber referensi (hanya-baca).

**Temuan utama: referensi mempunyai tipe yang PERSIS sama dengan format
kita.** `GGML_TYPE_PQ2_0` di `ggml-common.h`: `{ggml_half d; uint8_t
qs[32];}` = 2 bit/elem, grup 128, satu skala fp16 per 128 bobot. Itu
persis kontrak Bonsai-2. Codecnya: kode 2-bit -> int8 {-1,0,+1,+2} lewat
tabel PRMT `__byte_perm(0x020100FF, 0x020100FF, q)`; kode kita (q-1)*s
untuk q∈{0,1,2} adalah himpunan bagiannya.

**Dan referensi memakai INT8 tensor core, bukan FP16:**
- `mma.cuh` di sm_75: `mma.sync.aligned.m8n8k16.row.col.s32.s8.s8.s32`
  (Ampere memakai m16n8k32).
- Decode: `ggml_cuda_dp4a` (int8 dot product per warp).
- T4 resmi: 65 TFLOPS FP16 vs **130 TOPS INT8** -> 2× throughput.
- Skala fp16 dikalikan SEKALI setelah akumulasi int32, bukan per bobot.
- Aktivasi dikuantisasi ke Q8_1 sekali (`quantize_mmq_q8_1_cuda` /
  `quantize_row_q8_1_cuda`) lalu dipakai ulang seluruh ubin bobot.

Implikasi untuk target 100+ tok/s: port int8 MMA adalah daya terbesar
(2× TC), dan port dari rancangan yang sudah terbukti. Tapi menambah
galat (kuantisasi aktivasi int8) — referensi menerimanya, dan secara
eksplisit memilih MMQ di setiap batch untuk PTQ1_0 dengan komentar
"the fp16 dequantize + cuBLAS fallback is the source of PTQ1_0's extra
error on CUDA". Konfigurasi ubin referensi: I=128 (baris bobot), J=128
(batch), 256 thread, K_vram=256, stream_k=true, SMEM ≈ 56,5 KB.

Semua dicatat di CATATAN_IMPLEMENTASI_BONSAI2.md §12 (12a-12g).

## Verifikasi numerik prefill vs decode (bits=2)

Sebelum ini, jalur prefill batched 2-bit hanya divalidasi lewat koherensi
generasi + waktu, BUKAN perbandingan numerik dengan jalur per-token.
Mekanisme yang sudah ada: `BONSAI_DUMP_TOP2=1` (top-2 logit di batas
prefill) vs `BONSAI_PREFILL_PER_TOKEN=1` (loop decode per-token).
Aturan: token sama + selisih logit kecil = cocok; flip token tapi kedua
gap < 0,05 = wajar (urutan akumulasi fp16 WMMA vs GEMV); gap besar =
bug layout dicurigai.

`run_infer_2bit.py` bagian 6 ditulis ulang: dua run (batched vs
per-token) dengan prompt + max-tokens SAMA, parse [TOP2]/[GEN]/[PERF],
lalu VERDIK. Dirilis ke kernel okiabrian/bonsai-2bit-infer.
