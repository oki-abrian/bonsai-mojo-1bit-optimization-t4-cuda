## Akar crash rc=-11 `BONSAI_DUMP_ACT_DIR` DITEMUKAN (forensik biner)

Gejala (kernel v1..v3 `okiabrian/bonsai-act-dump`): setiap run dgn
`BONSAI_DUMP_ACT_DIR` diset SIGSEGV (rc=-11) tepat setelah
`>> [STEP] bobot global siap ...`, sebelum cetakan `[ACT-DUMP] aktif`.
Run A/C (tanpa env dump) lulus; bahkan run E dgn `BONSAI_DUMP_ACT_TOKENS=0`
juga crash => crash di `act_dump_configure` / `_ad()`, BUKAN di badan
`act_dump_site`.

Rantai panggilan: `act_dump_configure` (main.mojo:1077) -> `_ad()`
(act_dump.mojo:85) -> `khq_state_slot_cell(2)` (src/ops.mojo:1021).

**Penyebab (disassembly `bonsai_infer` build CPU, wheel
okiabrian/bonsai-build-cpu):** `khq_state_slot_cell` terkodekan sebagai

```
dlopen(so) -> dlsym("khq_state_slot") -> dlclose(so) -> call *fn
```

`dlclose` dipanggil SEBELUM lompatan tak-langsung. Bila `dlclose` menjatuhkan
refcount dlopen ke nol, glibc melepas pemetaan `.so`, dan `call *%r15` melompat
ke alamat tak terpetakan -> SIGSEGV. Bukti pendukung (objdump biner yg sama):

- `khq_state_slot_cell` @0x850e0: `0x852b9 get_symbol`, `0x852c4 callq
  dlclose@plt`, `0x852cb callq *%r15` — dlclose DULU.
- 7 titik FFI lain (khq_compress, khq_window_attn, khq_gather_q, khq_merge_gate,
  gdn_seq, QwenLinear1Bit::forward_device, khq_step) SEMUA memanggil simbol
  DULU, dlclose di epilog — hanya fungsi slot ini yg destruktor handle
  digeser kompilator ke depan pemanggilan ekor (Mojo 25.x, `return f(...)`).
- Fungsi C `khq_state_slot` (@0xfbf0 di .so) benar: kembalikan
  `&g_khq_slots[which]` dgn clamp `which>2 -> 0`. BUKAN penyebab.
- `.so` hanya NEEDED libc/libm/ld => dlopen pasti berhasil; hipotesis FFI
  gagal dibantah.
- `act_dump_configure` @0x94090 benar (cek NULL + `AlignedAlloc(8,0x58)` 88 byte
  = sizeof ActDumpGlobals). Bukan penyebab.
- src/ops.mojo mtime 2026-09-21 (sebelum v138) => kode sumber sama, ini
  masalah codegen, bukan edit terbaru.

Mengapa v138 (deploy_on_kaggle.sh, `pixi run mojo build --target-accelerator=
sm_75`) selamat: build GPU vs build CPU (wheel) menghasilkan kodegen berbeda
untuk urutan destruktor. Build CPU-lah yg rusak.

**Perbaikan (aditif, level driver, TANPA sentuh src/** atau main.mojo,
tanpa build ulang 20 menit):** `LD_PRELOAD=libbonsai_qmv_sm75.so` di env
`bonsai_infer`. Dgn preload, `.so` masuk peta tautan awal proses; `dlclose`
situ tak pernah menjatuhkan refcount ke nol => pemetaan tetap => lompatan
aman. Diverifikasi oleh probe terisolasi tahap 2c di
`kaggle_act_dump/run_act_dump.py` yg mereproduksi pola
dlopen->dlsym->dlclose->call di proses anak Python (mode "kodegen" =
tutup-lalu-panggil; mode "aman" = panggil-lalu-tutup), diuji tanpa dan dgn
LD_PRELOAD.

Status: kernel v4 (probe + LD_PRELOAD + matriks 6 run A..F + dump 20 task)
di-push ke `okiabrian/bonsai-act-dump`. Catatan: `PROBE_SRC` diuji lokal dgn
dummy dylib (rc=0 dua mode; macOS dyld tak melepas dylib, jadi simulasi
SIGSEGV-nya hanya relevan di Linux Kaggle).

## FORENSIK OBJDUMP v38: PERBAIKAN MENGUBAH URUTAN — TAPI BUKAN KASUS TAIL CALL

Disassembly `khq_state_slot_cell` @0x84e90 di biner v38:
```
85030 call get_symbol     ; f = h.get_function("khq_state_slot")
85035 mov  rbp, rax       ; simpan fn ptr
85038..8504d              ; dec refcount handle (bt r12,0x3e; lock dec; AlignedFree)
85052 mov  rdi, r13       ; r13 = handle h
85055 call dlclose        ; <-- DLCLOSE DULU
8505a mov  edi, r15d      ; which
8505d call rbp            ; <-- CALL *fn SETELAHNYA
8505f mov  [rbx], rax     ; dst[] = hasil
```

Di v38 dlclose masih mendahului call *fn. TETAPI bandingkan dgn biner v35
crash (fungsi return-value): `get_symbol(80ff9) → dlclose(81004) → call r15
(8100b)` — di v15 handle dimusnahkan SESAAT setelah get_symbol, TANPA
pemanggilan sama sekali sebelum dlclose. Di v38, refcount handle di-dec
(0x85038-8504d: `bt r12,0x3e; lock dec [r14-8]; jne; AlignedFree`) BUKAN
dlclose langsung. Lalu dlclose@85055 → call@8505d.

8 titik FFI lain di v38 (khq_compress 8525a→852b9→852e0, khq_window_attn
854c4→85513→8553a) memang memanggil dulu. Tapi pola sumber mereka berbeda:
`var ret = f(...)` di luar except, tanpa cabang `dst[] =` kedua.

**Koreksi atas catatan sebelumnya:** klaim lama "parameter keluaran mencegah
tail call" TIDAK TERBUKTI dgn melihat codegen — dlclose masih di depan call.
Penyebab sebenarnya belum diketahui; hipotesis yang lebih kuat: Mojo
menjadwalkan destructor `h` berdasarkan analisis lifetime (akar `try/except`
+ 2 cabang), bukan return-vs-dst.

**Implikasi (belum dievaluasi):** belum tentu SIGSEGV — dlclose hanya
melepas .so bila refcount dlopen turun ke nol. Di v38, `try_open_cuda_lib`
membuka handle baru tiap panggilan, dan `f` hanya dipanggil SEKALI dlm
fungsi. Apakah refcount global .so >1 (mis. dlopen lain aktif) di runtime
belum diuji. **LD_PRELOAD masih merupakan jaminan satu-satunya yg terbukti
(v4: 20/20 lulus). v38 tanpa LD_PRELOAD = hipotesis, bukan kesimpulan.**
